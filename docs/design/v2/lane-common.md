# Lane common brief (Lanes B, C, D of the v2 rollout)

Read this before your lane section in `03-build-lanes.md`. Lane A (tokens, fonts, shell, grid primitives, states, CategoryChip, AuditTape) has already landed on the branch `v2-registry-grid`; its exact exported signatures are in `docs/design/v2/lane-a-signatures.md`. Import from Lane A's files, never edit them. If you need a change there, say so in your report and use a local wrapper.

## Read in this order
1. `docs/design/v2/lane-a-signatures.md` (what you can import)
2. `docs/design/v2/DESIGN.md` and `01-direction.md` sections 4 and 5
3. your screens in `02-ux-concept.md` (sections 4 to 6 and the per-screen spec for your routes), and the comps `prototype/<screen>.html` with the PNGs in `prototype/shots/` (use the Read tool; it shows images). Also `prototype/shots/contact-sheet-vs-rivals.png`.
4. `frontend/AGENTS.md`: this Next.js has breaking changes. Read the relevant guide under `frontend/node_modules/next/dist/docs/` before writing route code.
5. `docs/spec/00-architecture-and-scope.md` hard rules, and ADR 0005 and 0007.

## Rules
- Do NOT run git. The controller commits. The branch is `v2-registry-grid`.
- Edit only the files your lane owns (listed in `03-build-lanes.md` and in your prompt). Never touch another lane's files, `globals.css`, `components/shell/*`, `components/grid/*`, `components/ui/*`, `CategoryChip.tsx`, `AuditTape.tsx`. If something in another lane's area blocks you, report it.
- Conventions win over the plan. If the plan contradicts the code, the API or a hard rule, say so in your report and do the right thing. The owner prefers being corrected to being obeyed.
- Hard rules: result and clinical text only from the API (never hard-code clinical wording in components); the closed vocabulary (`shared_result_found`, `no_shared_change_found`, `more_information_needed`); the three categories are not a scale; no red or green on results; every colour has a second channel (cell glyph, label, hatch); a detection rate, never a residual-risk number; no marriage-decision question or score; Western digits in all locales; logical CSS properties only (no `left`, `right`, `margin-left`, `padding-right`, `text-align: left` and so on; use `inline-start/end`, `text-align: start/end`); no hex or raw colour in TSX (tokens only); four states on every data surface (skeleton that mirrors the layout, actionable empty state, error with retry and correlation id, partial); no animation library (CSS motion only, with a `prefers-reduced-motion` branch; transform and opacity only); route JS budget 170 KB gzip per route (check the `next build` output); WCAG 2.2 AA (axe on every page you touch, in en, ar and ur); no em or en dashes in visible copy; never name an individual; "(synthetic)" follows a person's name (the API's `display_name` already carries it).
- Every new message key goes into all three of `src/messages/{en,ar,ur}/<namespace>.json` (parity test `src/i18n/messages.test.ts` must stay green). Arabic and Urdu copy is draft: keep it short and plain, mark it as draft the way the existing keys do. Use only your lane's namespaces for new keys.
- Radii 0, 2, 4, 6 px. No `box-shadow` (except the single dialog shadow token), no `backdrop-filter`, no `blur()`, no gradients (except the hatch inside `Cell`), no glow, no bounce. Hairlines, not cards, separate things. Do not build "icon + heading + text" card rows as page structure.
- Windows. Use pnpm in `D:\dev\bayan\frontend`. Several lanes work at the same time, so builds must not share a folder: ALWAYS build and serve with your own dist dir, e.g. `set BAYAN_DIST_DIR=.next-b` (PowerShell: `$env:BAYAN_DIST_DIR=".next-b"`) before `pnpm build` and `pnpm start`; use `.next-b` (Lane B), `.next-c` (Lane C), `.next-d` (Lane D), and your own port (B 3201, C 3202, D 3203). Never build into plain `.next` (the controller uses it). `pnpm typecheck`, `pnpm lint` and `pnpm test -- <paths>` are safe to run any time (other lanes' half-finished files may cause errors in files you do not own; ignore those and report only your own). Start servers only with a timeout, kill them by PID when done, and confirm nothing listens on the port. Do not leave servers running. Mock mode: `BAYAN_MOCK=1 BAYAN_INSECURE_COOKIE=1 BAYAN_DIST_DIR=.next-b pnpm start -p 3201`. Real-backend end-to-end is the controller's job at the end. Delete your `.next-<x>` folder when you finish.
- Playwright is installed in the repo: write node scripts with `createRequire('D:/dev/bayan/frontend/package.json')` then `require('@playwright/test')`, with timeouts on every navigation, and close browsers. Put scratch files in a `lane<X>` folder inside the scratchpad directory your prompt names, not in the repo. Persona cookies for screenshots: follow `e2e/helpers.ts`.
- Look at your own screenshots (Read tool) at 1440 and 390 for en and ar (and ur for the result and any Nastaliq-heavy page) and compare with the comps before reporting. A screen is not done until its render matches the comp's structure and you have looked at it.
- Tests: adapt, never delete or weaken. If a test asserts structure that the spec deliberately changed, update the test to the new structure and keep every assertion about behaviour and about text coming from the API. Add tests for new logic (threshold branching, locale-pairing, matrix state mapping, probe runner and so on) in vitest, plus e2e specs in your lane's area when the spec calls for it. Run `pnpm typecheck && pnpm lint` and the vitest files you touch; run the whole `pnpm test` at the end of your lane and report the numbers. Failures that belong to another lane's files: report, do not fix.
- ADRs: write one short record per real decision or cut in `docs/decisions/` using only your number sub-block: Lane B 0170-0173, Lane C 0174-0177, Lane D 0178-0179 (title format as the existing `0166-...` files; "Status: accepted (2026-11-20)").
- Final report (at most 300 words): what you built per screen, files changed, test numbers, what you overrode or found wrong in the plan, open issues, anything you could not verify, and where your screenshots are (copy final screenshots into `docs/design/v2/lane-<x>-shots/`).
