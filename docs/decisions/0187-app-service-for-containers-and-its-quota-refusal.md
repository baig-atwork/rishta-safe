# ADR 0187: Host Rishta Safe on Azure App Service for Containers (Linux); the subscription has no App Service quota, so nothing is deployed

- **Status:** Design decided by the controller (2026-11-20) and implemented in the Bicep and scripts; **not realizable on this subscription**: every App Service plan SKU has a quota of 0 in the regions tried. Supersedes [ADR 0185](0185-bayan-gets-its-own-container-apps-environment.md) for the hosting service. Follows [ADR 0186](0186-region-attempts-for-bayans-own-environment.md).
- **Date:** 2026-11-20
- **Deciders:** the controller (decision, order of regions, stop rule); the infra lane (implementation, attempts)
- **Supersedes / superseded by:** supersedes 0185 (own Container Apps environment). Amends [0180](0180-demo-hosted-in-france-central-design-target-uae-north.md) and [0183](0183-deploy-from-the-laptop-github-workflow-unverified.md) (commands now `az webapp`, not `az containerapp`). [0182](0182-in-memory-state-for-the-demo-single-replica.md) and [0184](0184-infra-hardening-cuts-for-the-demo.md) stand.
- **Evidence:** `infra/scripts/deploy.ps1 -Action Deploy` (real creation attempts, 2026-11-20); `az rest` on `Microsoft.Web/locations/<region>/usages` and `Microsoft.ContainerInstance/locations/<region>/usages` (read-only); `az deployment sub what-if`; the backend image built and run locally with `BAYAN_ENV=demo`.

## Context
Azure refused a second Container Apps environment on this Free Trial subscription (ADR 0186), and the controller rejected sharing the other entry's environment and rejected upgrading billing during the build. The remaining Azure service that runs a Linux container with HTTPS and a hostname unrelated to the other entry is App Service for Containers.

## Decision
1. **Everything Rishta Safe owns lives in one group `rg-bayan-demo-<region>`:** a Basic registry (`acrbayan...`), the identity `id-bayan-apps` with AcrPull (managed-identity pull, registry admin user off, no stored password), one **Linux App Service plan B1** (`asp-bayan-demo`, one instance), and two web apps on that plan, **`bayan-api-<suffix>`** and **`bayan-web-<suffix>`**. The suffix is the first six characters of `uniqueString(subscription id)`: stable for this subscription, different for another, so the global `*.azurewebsites.net` names do not collide.
2. **Both apps:** `httpsOnly`, minimum TLS 1.2 (also for the SCM site), FTP and FTPS disabled, `alwaysOn`, HTTP/2 on, `WEBSITES_PORT` 8000 (api) and 3000 (web), `WEBSITES_ENABLE_APP_SERVICE_STORAGE=false`, one worker. The api has health check path `/healthz` and the settings `BAYAN_ENV=demo`, `BAYAN_DEMO_MODE=true`, `BAYAN_LOG_JSON=true`, and `BAYAN_SESSION_SECRET` from a secure Bicep parameter (generated by `RandomNumberGenerator`, kept in `infra/.secrets/`, never printed; an app setting, encrypted at rest and not readable with Reader access). The web app's `BAYAN_API_URL` is the api app's `https://` address.
3. **The api cannot be internal-only on this design, and that is a real change from ADR 0182's Container Apps layout.** App Service Basic has no virtual network integration for inbound traffic and no private endpoint, so `bayan-api` has a **public https address**. What that means, stated plainly: anyone who knows the address can call it. Every endpoint except health, the demo personas and cases, the governance declarations and the third-party refusal requires a bearer token (read from `backend/tests/integration/test_demo_flow.py`), and a demo persona's token is issued by the public `GET /v1/demo/personas` in demo mode, which is how the demo works. Everything the api serves is **synthetic** (made-up couples, no personal data), the tokens are simulated, and the audit chain records access. The web app is therefore a convenience, not a security boundary. This is acceptable only because of the synthetic data; any real data would need the parked private-networking work (parking lot).
4. **State is in memory, so exactly one instance** (the plan has capacity 1; B1 has no autoscale). A restart, a deploy or a platform move resets the demo ([ADR 0182](0182-in-memory-state-for-the-demo-single-replica.md)).
5. **Phases, each idempotent:** (1) group, registry, identity, AcrPull, plan; (2) the api app (needs its image); (3) the web app (needs its image and the api's address). The web app is not deployed until the controller says the frontend builds.
6. **Regions, in order:** `uaenorth`, then `germanywestcentral`. **If both refuse, stop**, clean up only the attempt's own new group, record the errors here, and do not try other billing options or touch the other entry's environment.

## The attempts (2026-11-20)
The subscription id is shown as `<subscription-id>`.

| # | Region | Outcome | Exact error |
|---|---|---|---|
| 1 | `uaenorth` | **Refused** when the plan was created (the group, registry and identity existed for a minute and were deleted with the group: this attempt's own new group only). | `Unauthorized` on `Microsoft.Web/serverfarms/asp-bayan-demo`: "Operation cannot be completed without additional quota. Additional details - Location: Current Limit (B1 App Service instances): 0 Current Usage: 0 Amount required for this deployment (B1 App Service instances): 1 (Minimum) New Limit that you should request to enable this deployment: 1. ... To request a quota increase, go to the Azure portal Quotas page (https://aka.ms/azure-quota), set Provider to App Service, then create a New Quota Request. Alternatively, try a different region or a lower App Service Plan SKU or worker count." |
| 2 | `germanywestcentral` | **Refused at preflight, nothing created.** | `SubscriptionIsOverQuotaForSku` (resource provider `Microsoft.Web/serverFarms (2025-03-01)`, `ValidationForResourceFailed`): the same text, "Current Limit (B1 App Service instances): 0 ... New Limit that you should request to enable this deployment: 1." |

**It is not a B1 problem.** The read-only usages API lists 67 App Service SKUs (F1, D1, B1 to B3, S1 to S3, P-series, Y1, ...) and **every one has a limit of 0** in `uaenorth`, `germanywestcentral`, `francecentral`, `northeurope` and `eastus`; `westeurope` and `swedencentral` list only one entry and `uaecentral` returned an error (not tested further). **Azure Container Instances** are the same: `StandardCores` has a limit of 0 in `uaenorth` and `germanywestcentral` (`ContainerGroups` 100, which is not enough without cores). So this Free Trial subscription cannot run any compute except the one Container Apps environment that the other entry holds.

After the attempts (`az`, read-only): neither `rg-bayan-demo-uaenorth` nor `rg-bayan-demo-germanywestcentral` exists; the only resource groups are the two belonging to the other entry, which were not touched. Failed deployment records `bayan-p1-*` remain at subscription scope (metadata, no resources).

## What was verified without Azure
The api image builds from `infra/docker/backend.Dockerfile` (76 MB, uid 10001), starts with `BAYAN_ENV=demo` now that every lane service exists, is healthy, and the api-only part of `infra/scripts/smoke.ps1` passes against it locally: `/healthz`, `/readyz` (5 services), 24 personas, 10 cases, a couple member's result in Arabic (category `shared_result_found`, 31 blocks, checker ok, staff-only fields absent), the staff view, an employer request refused with 403 citing Art. 19 to 21, and the audit chain still ok (length 55 to 56). The App Service Bicep builds, lints clean and passes ARM validate and what-if (what-if lists only changes inside the Rishta Safe group). **Never exercised on Azure:** the plan, the two apps, the managed-identity registry pull, the health check.

## Options (none done; the controller has ruled out billing changes and the other entry's environment)
1. **Request App Service quota** on the Azure portal Quotas page (provider App Service, B1, a chosen region). Free Trial subscriptions normally cannot raise this; not tried because it is a request, not a read.
2. **Host Rishta Safe outside Azure for the demo**, for example the existing `docker-compose.yml` on the laptop behind a public tunnel, or another container host. The images are the same.
3. **Revisit the options in ADR 0186** (upgrade billing, a second subscription) if the controller changes the ruling.

## Consequences
- The Bicep, `deploy.ps1` (actions Validate, Infra, Build, Deploy, Warm, Smoke, Status, Teardown), `smoke.ps1`, the workflows and the runbook are ready for the App Service design; a first real deployment waits on quota.
- **Cost of being wrong:** a document says Rishta Safe is hosted on Azure when it is not. Mitigation: nothing may be said about hosting until `deploy.ps1 -Action Status` prints a live location; the wording is in the runbook.

## Revisit trigger
App Service quota is granted, or the subscription changes.
